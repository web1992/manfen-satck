# TDD Bug Fix

修 bug 且有清晰、廉价的测试路径时，先让错误行为可执行，再改生产代码。目标是一条聚焦的回归测试：修前失败、修后通过。

不切实际时不要硬写测试。若可用测试需要大范围 harness 搭建、脆弱 mock、缓慢端到端基础设施、仅生产环境才有的状态、模糊复现步骤，或大量无关 fixture 变动，则跳过新增测试，改用最接近且有用的验证方式。

## Workflow

1. **理解 bug。** 弄清预期行为、当前行为、受影响路径，以及最小可观察复现。
2. **选最窄的可执行检查。** 优先用该代码路径上已有的最近 unit / component / integration / regression 测试。若没有明显可行的测试路径，不要仅为满足流程从零造一个。
3. **先写失败测试。** 加上能抓住该 bug 的最小聚焦测试。测试应编码预期行为，而不是镜像当前实现。
4. **修之前先跑新测试。** 确认它因预期原因失败。若通过了，或因无关原因失败，先改对测试或复现，再动实现。
5. **修 bug。** 做能满足预期行为的最小生产改动，同时保留周边契约。
6. **重跑回归测试。** 确认测试现已通过。

## If a Failing Test Is Impractical

改用最接近的可执行回归检查：定向脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可没有新测试，也不要坏测试。坏测试主要测 mock、编码当前实现细节、依赖时序或无关全局状态、为小修复依赖昂贵基础设施，或证明修复后马上会被删掉。

## Guardrails

- 不要仅为迁就错误实现而改测试。
- 不要弱化已有断言，除非预期行为确实变了且理由清楚。
- 让回归测试聚焦在这个 bug 上。避免大范围 fixture 变动或无关覆盖扩张。
- 若 bug 不稳定，尽量让测试确定性，并写明被锁定的信号。
- 若 bug 暴露更广的一类失败，先落地聚焦的回归路径，再考虑额外的姊妹覆盖。

## Final Response

汇报证据，而不只是结果：

- 点名修前失败的测试或可执行检查，以及它产生的失败。
- 点名修后通过的测试运行，以及做了哪些周边验证。
- 若无法展示修前失败证据，说明原因，并描述改用的最接近回归检查。
