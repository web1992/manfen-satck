# Model the Domain

用数据结构编码真实领域，而不是把它散在各类条件分支里。与领域匹配的结构会让非法状态无法表示，并消掉分支。写代码当下选好结构很便宜；事后再补救读起来像重构，往往被一拖再拖。

可考虑：

- 用状态机替代散落的 boolean、阶段或生命周期检查。
- 用类型化模型替代松散参数或反复出现的形状假设。
- 用 map、registry、查找表或 discriminated union 替代散布在多文件里的分支。
- 用 reducer 或 command/event 模型替代随意的状态 mutation。
- 用围绕一块领域知识组织的模块，替代 load、validate、transform、save 这类执行顺序。执行顺序不等于所有权。
- 用小的模块边界收拢重复的行为、所有权或不变量。
- 在访问模式需要时，用 queue、cache、index、graph、tree 或规范化集合。
- 任何其他合适的结构。若都不合适，先弄清代码绝不能允许什么、数据如何被读取，再找能精确编码这些约束的结构。

不要硬套抽象。若当前形状已经清晰、局部且不太会膨胀，宁可保持乏味的代码。对只增加间接层、却不减少分支、重复规则、非法状态或生命周期风险的抽象，保持怀疑。

漏做这一点的征兆是：新功能在既有 if/else 链上又多一个分支，或第二个 boolean 须与第一个保持同步。按时间阶段拆模块也是征兆：以阶段命名的模块会在各步重复同一套领域规则。
